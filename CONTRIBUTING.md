# Contributing to Dispatch

Thanks for your interest in improving Dispatch! This guide covers local setup, the project's
engineering rules, and the PR process.

## Development setup

Dispatch is a Bun + Turborepo monorepo (`apps/api`, `apps/web`, `apps/tracking-worker`,
`packages/shared`).

```bash
# 1. Install workspace dependencies
bun install

# 2. Start the backing services (Postgres, Valkey, MinIO)
docker compose up -d postgres valkey minio

# 3. Configure your environment — see docs/SELF-HOSTING.md for the full variable list.
#    At minimum set ENCRYPTION_KEY (32-byte base64):
bun -e "console.log(Buffer.from(crypto.getRandomValues(new Uint8Array(32))).toString('base64'))"

# 4. Run the API (migrations run automatically at boot)
cd apps/api && bun run dev

# 5. In another terminal, run the web app
cd apps/web && bun run dev
```

Run the test suite from `apps/api` (the suite runs under Vitest — use `bun run test`, **not**
`bun test`, which invokes Bun's native runner and cannot resolve the `vitest` mocking helpers):

```bash
cd apps/api && bun run test
```

See **[docs/SELF-HOSTING.md](docs/SELF-HOSTING.md)** for the full environment/deploy reference and
**[docs/DELIVERABILITY.md](docs/DELIVERABILITY.md)** for email-authentication guidance.

## Project rules (R1–R9)

These are enforced in review; PRs that break them will be sent back.

- **R1 — TypeScript only.** Every source file is `.ts`/`.tsx`. No plain JS, no untyped escape
  hatches (`any` only as a last resort, with a stated reason). Aim to keep files small.
- **R2 — Data-driven.** User-facing categories, labels, and options come from the database at
  runtime — never hardcoded as constants/enums/unions. (Program structure — types, schemas,
  handlers — is of course code.)
- **R3 — shadcn primitives.** Build UI only from shadcn primitives; never hand-roll an element
  styled to mimic one. Plain layout `<div>`s (flex/grid/spacing) are fine.
- **R4 — Migrations are generated.** Change the schema only in the Drizzle schema file, then run
  `bunx drizzle-kit generate` from `apps/api/`. Never hand-write or edit a migration.
- **R5 — Prove it.** Before "done": `bun typecheck` clean, `bun lint` clean, tests green.
- **R6 — No fabrication.** If you can't find something, say so — don't invent it.
- **R7 — Simplicity first.** The minimum code that solves the task; no speculative abstractions.
- **R8 — Surgical changes.** Touch only what the task requires; don't reformat or "improve"
  adjacent code that isn't broken.
- **R9 — Security is structural.** Scope every read/write to its owner/tenant; derive identity
  server-side from the session (never trust a client-supplied owner/tenant/role). Secrets live
  server-side, encrypted at rest, never returned to the browser. Validate inputs at every
  boundary with Zod.

## Branch & commit conventions

- Branch off `main`; use a descriptive branch name.
- Use [Conventional Commits](https://www.conventionalcommits.org/) prefixes: `feat:`, `fix:`,
  `docs:`, `chore:`, `refactor:`, `test:`.
- **Do not add AI-assistant attribution** (e.g. `Co-Authored-By` for an AI tool, or "generated by"
  trailers) to commits, PRs, or code comments.

## Pull-request process

1. Ensure `bun typecheck`, `bun lint`, and the test suite all pass locally.
2. Open a PR against `main` with a clear description of what changed and why.
3. CI must be green. The **required** jobs are: Build, Test (api + worker), Secret scan
   (gitleaks), and Compose validate. The Quality (typecheck/lint/web-tests) and Security-scan
   (`bun audit`, CodeQL) jobs are advisory today — don't add new problems to them.
4. A maintainer reviews for correctness, the R1–R9 rules above, and security.
